# Phase 6.1 Plan 03: Provisioning of the shared records database Summary

`tools/deploy.mjs` now provisions the records database without deleting anything and can be run again safely. It creates `zuma-scores` (read back), applies its two `CREATE TABLE IF NOT EXISTS` statements (read back through `sqlite_master`), binds `SCORES_DB` next to `ASSETS_DB` in one PATCH on production and preview (read back), then redeploys the worker on `main`. The worker now gets the pack's level ids (`recordLevelIds(dist/assets/pack.json)`). `--plan`, `--dry-run`, `--rollback-plan` and `--verify` describe the new steps. The existing guarantees still hold: no DELETE, PATCH only on the Pages project, SQL limited to the explicit whitelist, no row written to `zuma-scores`, nothing secret in the output.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Redeploy after a new binding**
- **Found during:** Task 2
- **Issue:** The default pipeline redeployed the worker only when its marker differed. Pages applies a binding change only to new deployments, so a PATCH adding `SCORES_DB` with an unchanged worker would have left production without the binding. `planD1.deploy` already said `bind || …`, so the pipeline and the plan disagreed.
- **Fix:** The pipeline now redeploys when the PATCH happened (`rebound || !deployedOk`). This is locked by the r222 test « zuma-scores present but without its tables », which expects the schema, the PATCH and then the deployment.
- **Files modified:** tools/deploy.mjs
- **Commit:** 613faf2

**2. [Rule 3 - Blocking] Temporary bridge in deploy.mjs between the two tasks**
- **Found during:** Task 1 GREEN
- **Issue:** The new `bindingOk` / `bindingBody` signatures broke the existing `deploy.mjs` pipeline, so `npm test` would have failed on the Task 1 GREEN commit.
- **Fix:** 8a2a8d3 kept `deploy.mjs` on ASSETS_DB only through `boundTo`. 613faf2 removed that bridge entirely.
- **Commit:** 8a2a8d3 (removed in 613faf2)

**3. [Rule 3 - Blocking] planD1 test in r220-d1 adjusted**
- **Issue:** The test « planD1: … an incomplete key is planned again » expects `bind` to be false on a bound project. Under the two-database contract that needs `scores` and both bindings.
- **Fix:** That test now passes `scores` (database + both tables) and `bindingBody(UUID, S_UUID)`. Its assertions are unchanged.
- **Commit:** 92542d6

**4. [Rule 3 - Blocking] r220-deploy `--plan` count and rollback numbering**

- **Fix:** Both were updated with the « R2.0.22: shared records database (plan 06.1-03) » comment.
- **Commit:** 2140203
