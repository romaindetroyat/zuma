# Phase 6.1 : Records partagés — contexte

**Demande de l'utilisateur (2026-10-11)** : « Pour les meilleurs temps, tu peux indiquer le prénom de celui qui l'a réalisé ? Les scores, records etc… sont en commun pour tous les joueurs que j'invite, ou chacun le sien ? » — réponse à la question posée : **« Les deux »** (un tableau commun à tous les invités ET les records personnels de chacun).

État avant la phase : tout est local au navigateur (`localStorage`) — meilleurs scores de l'aventure (10, `src/progress.ts`), meilleur temps par niveau (`bestTimeKey`, `src/statsdialog.ts` / `main.ts`). Le prénom vient de `api/me` (D-12 de la phase 6, worker `tools/d1worker.mjs`, table privée `players`). Remplace la synchronisation reportée D-39 / D-42 de la phase 5 (fonction Pages + D1 identifiée par l'utilisateur Access).

## Décisions

- **D-01 Périmètre** : version hébergée seulement (`--deploy`, derrière Access). Le standalone (`file://`) et le serveur local gardent le stockage local actuel ; ils affichent aussi le prénom (profil local) à côté du meilleur temps.
- **D-02 Deux portées** : « Tous les joueurs » (commun à toutes les adresses autorisées) et « Mes records » (par identité Access, identiques sur tous les appareils du joueur).
- **D-03 Données** : meilleurs scores de l'aventure (10 communs, 10 personnels) et meilleur temps par niveau (le meilleur commun avec le prénom de son auteur, et le meilleur personnel). Rien d'autre.
- **D-04 Identité** : le prénom est apposé par le serveur à partir de l'e-mail du JWT Access (table `players`, D-12) ; le client n'envoie jamais de nom. Adresse autorisée sans prénom → « Joueur ». Aucune adresse stockée : clé = SHA-256 de l'e-mail en minuscules (comme `playerKey`).
- **D-05 Stockage** : base D1 distincte `zuma-scores`, liaison `SCORES_DB` (la base `zuma-assets` reste réservée au contenu). Créée et munie de son schéma par `tools/deploy.mjs` (idempotent, lit avant d'écrire, ne supprime jamais rien ; `--plan`, `--dry-run`, `--rollback-plan` à jour).
- **D-06 API du worker** (même origine, JWT Access obligatoire comme le reste) :
  - `GET /api/records` → `{ shared: { scores, times }, mine: { scores, times } }` en `no-store` ;
  - `POST /api/records` (JSON) pour un score d'aventure ou un temps de niveau ; seule méthode d'écriture du worker, uniquement sur ce chemin ; `Origin` = l'hôte, `content-type` JSON, corps borné ; réponse = le nouvel état (même forme que le GET).
- **D-07 Hors ligne d'abord** : le local reste la vérité de l'appareil ; les envois en attente sont mis en file (localStorage) et vidés au chargement, au retour du réseau et après chaque niveau ; la dernière copie du serveur est gardée pour l'affichage hors ligne. Aucune attente réseau ne bloque le jeu (délai court, échec silencieux).
- **D-08 Reprise de l'existant** : au premier échange réussi, chaque appareil envoie ses meilleurs temps locaux et les scores de son tableau local inscrits sous le prénom du joueur courant (jamais les entrées de démonstration).
- **D-09 Affichage** (avec les graphismes du jeu, pas de panneau DOM) :
  - STATS de fin de niveau : meilleur temps commun avec le prénom (« 1:23 (Sophie) ») ; si le record personnel diffère, il est indiqué aussi, dans la grille originale ;
  - écran d'aventure : la plaque RECORDS (3 lignes) montre le tableau commun ; un toucher / clic sur le titre RECORDS bascule « Tous » / « Moi » ;
  - écran de fin : tableau des 10 communs avec la ligne du joueur en surbrillance, même bascule « Tous » / « Moi », et le score de la partie.
- **D-10 Confiance** : les invités sont de confiance ; le serveur ne vérifie que des bornes (score entier 0..99 999 999, temps entier 1..3 600 s, identifiant de niveau du pack, longueur des champs) et limite le débit par identité ; rien d'autre (pas d'anti-triche).
- **D-11 Qualité** : règles pures (fusion « le meilleur gagne », file d'attente, bornes) dans `src/` testées en Node ; worker testé avec une D1 simulée (comme `tests/r220-d1.test.mjs`) ; la règle CLAUDE.md « toute règle modifiée est verrouillée par un test » s'applique.
- **D-12 Livraison** : version R2.0.22, notes de version, README (section hébergement et ajout d'un joueur), CONCERNS, UAT ; déploiement par l'orchestrateur après accord de l'utilisateur ; aucune adresse, aucun prénom réel dans le dépôt (placeholders `example.org`).
