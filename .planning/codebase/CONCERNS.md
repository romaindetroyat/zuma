## Security Considerations

- Données utilisateur, toutes locales à l'appareil : meilleurs temps par niveau, profil (nom, étage maximal), partie sauvegardée, tableau des scores (voir « Stockage local (R2.0.21) ») ; sur la version hébergée, le prénom vient de l'identité Access par `api/me` (D-12)
- Les ressources originales sont propriétaires : ne jamais les publier ; `tools/guard.mjs` + CI bloquent les extensions et dossiers sensibles

**Modèle légal de la PWA (D-42, R2.0.20):**
- Le dépôt public et la CI ne contiennent et ne construisent que le **code** (repli procédural et rendu vectoriel sans pack) ; la garde est inchangée et passe dans `npm test` et en CI
- L'artefact `npm run deploy` (`node tools/build.mjs --deploy`) contient le **pack original** ; il est produit localement dans `dist/` (ignoré par Git), refuse l'absence de pack et journalise « à héberger uniquement en privé ». Il ne doit être hébergé **qu'en privé**, derrière Cloudflare Access, par `npm run deploy:private` lancé à la main avec le jeton de l'utilisateur (plan 05-16 : Access en place ; le contenu est envoyé depuis le Mac, voir « Hébergement privé » ci-dessous). Jamais par le dépôt ni par la CI, jamais de publication publique (pas de GitHub Pages)
- La liste d'accès reste restreinte (adresses `allow` et `players` de `private_assets/deploy.json`) : ouvrir le jeu au public reviendrait à distribuer les ressources de PopCap (D-42)
- **`api/me` (D-12, R2.0.21)** : le worker généré (`tools/d1worker.mjs`) répond `{ name }` pour l'adresse du JWT Access validé, 404 sinon, 403 sans jeton. Il ne contient que les empreintes SHA-256 des adresses (minuscules, espaces retirés) et les prénoms ; aucune adresse ni aucun prénom n'est dans le dépôt. Toute adresse de `players` est autorisée par `readConfig`. Côté jeu, la réponse n'est acceptée que si c'est un JSON `{ name: string }`, passe par `sanitizeName` et n'est dessinée que sur le canvas ; la requête n'est faite ni sur `file://`, ni sans pack, ni sur une adresse locale. Une empreinte SHA-256 d'adresse e-mail reste devinable par dictionnaire ; le source du worker n'est jamais servi (il s'exécute chez Cloudflare) et vit seulement dans `dist/_d1/` (ignoré par Git) lors d'une répétition à blanc
- Le standalone (fichier unique avec le pack) suit la même règle : livré à l'utilisateur hors dépôt, jamais commité (`standalone/` ignoré)
- Le service worker ne met en cache que la même origine en GET et ne touche jamais `api/` ni `cdn-cgi/` (cookies d'Access, futurs appels de scores)

**Stockage iOS / Safari (R2.0.20):**
- L'app de l'écran d'accueil a un **stockage isolé** de Safari : elle doit être ouverte une première fois **en ligne** pour mettre le jeu et le pack en cache, même si Safari les a déjà
- Le stockage peut être **évincé** après une période sans utilisation, faute de stockage persistant (`navigator.storage.persist()` est demandé, sans garantie sur iOS) ; un effacement des données du site retélécharge tout à la visite suivante (en ligne)
- Taille du cache ≈ taille du pack : ≈ 6 Mo (6 074 436 octets mesurés dans Chromium en 05-14), affichée dans la vue Aide

**Stockage local (R2.0.21):**
- Clés `localStorage` : `zuma.profile.v1` (`{ name, maxStage, source? }`), `zuma.save.v1` (`{ stage, level, score, lives }`, écrite au début de chaque niveau, effacée au game over et à la fin), `zuma.highscores.v1` (`{ adventure: [10 entrées { name, score, stage, level, date }] }`) ; existantes : `zuma.best.<id>`, `zuma.sfx`, `zuma.pixelated`, `zuma.install.hidden`
- Lectures défensives (`parseProfile`, `parseSave` bornée par la taille des étages du pack, `parseScores`) ; tout accès passe par un stockage injecté sous try/catch (`readJson` / `writeJson`) ; une revue `?level=` n'écrit rien
- **Effacer les données du site** (réglages du navigateur, éviction iOS) perd le profil, la sauvegarde et le tableau des scores ; l'app installée sur iOS a un stockage séparé de Safari (donc son propre profil et ses propres scores)
- **Aucune synchronisation** entre appareils : différée (phase 5 D-39 / D-42 ; fonction Pages + D1 identifiée par Access). Le prénom D-12 est commun à tous les appareils d'une même adresse, le tableau non

**Limites de vérification (R2.0.20):**
- WebKit n'est pas installé sur le banc : iPhone et iPad ont été **émulés dans Chromium** (taille d'écran, agent utilisateur, toucher, `navigator.standalone` simulé). Non vérifiés : marges sûres réelles (`env()` vaut 0 dans Chromium), stockage isolé de l'app, `navigator.audioSession`, déblocage audio de Safari, « Sur l'écran d'accueil » et « Ajouter au Dock » réels
- L'installation réelle sur iPhone / iPad (UAT 9) attend un hébergement **HTTPS** : un iPhone ne peut pas installer une PWA servie en `http://<IP locale>` ; Mac / PC sont vérifiables tout de suite sur `http://localhost:8080/`. L'hébergement privé (05-16) fournit cette adresse HTTPS dès le premier envoi du contenu depuis le Mac

**Hébergement privé (05-16, Cloudflare Pages + Access):**
- **Méthode One-time PIN de l'organisation** : elle est ajoutée à toute l'organisation Zero Trust. Pour que les applications existantes (`allowed_idps` vide, donc ouvertes à toutes les méthodes) gardent exactement leur connexion actuelle, leur `allowed_idps` a été fixé au seul fournisseur Cloudflare avant l'ajout (D-43). Cette étape est journalisée et réversible : remettre `[]`. Une application créée plus tard avec `allowed_idps` vide acceptera aussi le code par e-mail, et la sécurité de cette connexion dépend alors de la boîte de réception de l'adresse autorisée. `tools/deploy.mjs` refuse d'ajouter la méthode tant qu'une application existante sans fournisseur imposé n'est pas listée dans `pinIdpApps`
- **Politique dédiée « Zuma — joueurs »** : la politique existante « Romain uniquement » est partagée par les applications du compte. Le jeu a donc sa propre politique, pour qu'une adresse ajoutée pour le jeu n'ouvre jamais les autres applications
- **Vérification HTTP** : depuis la session cloud, `*.pages.dev` et le domaine de l'équipe sont injoignables (CONNECT refusé par le proxy). `--verify` répond alors 2 : la configuration est prouvée par l'API, la protection HTTP se vérifie en navigation privée. De plus, le proxy remplace l'en-tête `Authorization` de toute requête vers `api.cloudflare.com` : le jeton d'envoi de Pages n'arrive pas (403 `8000013`), d'où l'envoi depuis le Mac
- **R5, mise à jour après expiration** : quand la session Access a expiré, la requête du nouveau `sw.js` est redirigée et la mise à jour échoue en silence. L'app installée continue sur sa version en cache (cache d'abord) jusqu'à la prochaine connexion en ligne. Accepté, aucun message dédié
- **R2, iOS** : la connexion dans l'app de l'écran d'accueil (stockage séparé de Safari) n'est pas prouvée. Une boucle de connexion orienterait vers la variante « Access par chemins » (M-A du spike 05)
- **Retrait** : `node tools/deploy.mjs --rollback-plan` imprime les étapes sans rien exécuter. Il faut supprimer le projet Pages d'abord, puis les applications Access et leurs politiques si elles ne servent plus, pour qu'aucun instant ne laisse le pack sans protection. La méthode One-time PIN peut rester ; si elle est retirée, les applications épinglées peuvent revenir à `allowed_idps` = `[]`

## Performance

- `Track.nearest` est O(points) par projectile et par tick (≈3000 points sur les pistes originales) : acceptable (< 5 projectiles), à indexer si besoin
- Composition alpha des feuilles de sprites faite une fois au chargement
- Écran STATS composé à l'échelle du magasin de pixels dans un canvas enfant (≈ 2 000 × 1 500 à 3,1 ×, borné à 4 ×) et recomposé à chaque ligne révélée, chaque pas du compte à rebours (100 ms) et chaque état du bouton : 0,8–1,6 ms par composition mesurés à 3,125 × avec le kit 2 × (1,5–2,2 ms en 1 ×, plan 05-08) — sans PNG intermédiaire depuis R2.0.17
- Actifs 2 × EPX (polices, pièces du dialogue, bouton, billes, ombre, icônes, barre de menu) construits une seule fois dès que l'échelle atteint 1,5 et jamais en « Pixels nets » : 40 images, 16,26 Mio mesurés avec le pack (barre de menu 4,69 Mio en pleine 640 × 480, six feuilles de billes 4,4 Mio) ; la bascule 1 × ↔ 2 × ne reconstruit rien. Réduction possible : recadrer la barre de menu sur ses lignes opaques, partager une ombre entre les feuilles

## Fragile Areas

- Versions et caches du service worker (R2.0.20) : le shell est versionné par **build** (`zuma-shell-<build>`), le pack par **empreinte** (`zuma-assets-<sha256 12>`) ; `activate` supprime tout autre cache. Changer le nommage, ou servir le shell depuis le cache du pack, ferait coexister deux versions ou retélécharger le pack ; chaque version doit lire ses propres caches (pas de `caches.match` global). Le verrou `r217` lit encore la liste `SHELL` littérale du modèle `public/sw.js`
- Standalone concaténé (R2.0.20) : `pwa.ts` rejoint `MODULES` après `original` ; les noms de premier niveau de tous les modules partagent une seule portée dans `standalone/zuma-standalone.html` — un nouveau nom de premier niveau qui en double un autre casse le fichier unique (verrous `r215-presentation`)
- **Noms de premier niveau uniques entre `progress`, `welcome`, `adventure` et `main`** (R2.0.21) : les trois nouveaux modules sont concaténés avant `main` dans le standalone ; leurs constantes et fonctions (`MM`, `ADV`, `drawWelcome`, `drawAdventure`, `mmDialogFrame`…) doivent rester préfixées et uniques. Les helpers de dialogue partagés sont exportés par `welcome.ts` et importés par `adventure.ts` : l'ordre `progress → welcome → adventure → main` de `MODULES` doit être gardé (verrous `r215-presentation`, `r218-presentation`, `r221-*` « bundle »)
- **Machine d'états, seul chemin entre écrans** (R2.0.21) : toute transition (fin de niveau, menu, portes, dieu, fin) passe par `Game.dispatch` → `reduceApp` → effets ; `main.ts` ne doit jamais relancer un niveau ni écrire le stockage en dehors des effets (`start-level`, `save-*`). Les verrous `r221-adventure` / `r221-welcome` lisent `main.js` compilé (pas de `this.progress = { stage: 0, level: 0 }`, `closeStats` → `won` / `retry` / `leave`, game over par `checkOutcome` une fois par niveau)
- Le plateau figé sous le dialogue du dieu : `enterScreen` garde le moteur pour l'écran `temple` seulement, sans jamais le faire avancer ; tout autre écran hors niveau le libère
- Mise en page de l'astuce (05-15) : la colonne de deux lignes et le paragraphe de trois lignes dépendent des largeurs d'`Arial12Bold` et de la boîte (`STATS_LAYOUT.tip`) ; toute modification de la boîte ou de l'étiquette doit garder les sept astuces complètes (verrou `r220-tip`, actif seulement avec le pack)
- Les sons du contact et de l'impact (R2.0.19, `SOUND_MAP` de `tools/import-original.mjs` : `insert` → `ballclick2`, `merge` → `ballclick1`, plus de `powerup`) n'agissent qu'après **réimport du pack** : un pack plus ancien garde les deux clics inversés
- La cinématique de la chaîne est exprimée en **temps maj** (`majClock`, compteurs `v`, recul en px/maj convertis) : toute nouvelle règle de mouvement doit passer par la même horloge, sous peine de décaler les contacts d'un tick ; les tests `r219` lisent la phase de l'horloge plutôt que des instants codés en dur
- Le décodage CURV aligné (R2.0.18) n'agit qu'après **réimport du pack** (`npm run import`) : un pack importé avant R2.0.18 garde les drapeaux décalés d'un point et l'ancienne lecture « caché », et n'a pas les images `slidertrack` / `sliderthumb` / `checkbutton` (menu en repli vectoriel). Aucune courbe du pack n'a de priorité ≥ 2 : les passes 2–4 ne sont exercées que par les tests
- L'ordre de dessin est porté par `drawPasses` (pur) et par le découpage de `draw()` en passes : toute nouvelle couche du plateau (particules, effets) doit recevoir une priorité (`ballPriority` de sa chaîne, 4 par défaut) sous peine de passer sous les découpes ; les étincelles du décompte prennent la priorité du `s` porté par l'événement `cleanup` (pas de recherche du point le plus proche, fausse sur les courbes qui se croisent)
- Le menu de jeu est un `<canvas class="menu-picture">` enfant de `#menu`, recomposé à chaque état ; `bindInput` doit rester défini après `bindPanels` dans `main.ts` (un verrou `r217` lit le premier `addEventListener('pointerdown'` compilé)

- `tests/r211` vérifie la CSS après le dernier marqueur littéral `R2.0.11` : conserver ce marqueur et les sélecteurs compacts
- `tools/build.mjs --standalone` dépend du dépouillage regex des `import/export` : éviter `export { … }` et les `export default` ; `src/upscale.ts` doit rester une feuille (seul `original.ts` l'importe à l'exécution) pour que l'ordre de concaténation `MODULES` tienne
